# 自举与迭代计划（Bootstrap Plan）

> **用途**：回答"是不是先做一种图、再自举迭代出新的图类型"，并把自举的**顺序、判据、停止条件与防自嗨规则**定下来。
> **目标读者**：实现者（M1 排期）、评审者。
> **状态**：v0，核验于 2026-11-03；据此调整 M1 计划（见 §6）。
> **关联文档**：[profiles-catalog-v0.md](profiles-catalog-v0.md)、[engine-architecture-v0.md](engine-architecture-v0.md)、[to-dolist.md](../to-dolist.md)。

---

## 1. 核心判断：内核做一次，剖面可插拔

**不是**"先做一种图，再照着复制出十种"。那样第十种图一定会逼你改内核。

正确形态是：

```
内核 kernel@1（元素/关系/批注/约束/视图）  ← 只做一次
        ↑ 数据驱动
剖面 c4-container@1 / dfd@1 / er@1 / …    ← 只加数据，不改代码
```

**自举的真正作用**不是"扩展图类型的花样"，而是**验证内核抽象是否够**：

- 加第 2 种图（DFD）时，如果需要改内核 → 内核抽象错了，停下来修；
- 加第 5 种图（sequence，需要专用布局）时，如果布局接口不够 → 接口设计错了；
- 如果 12 种图都只是"加一个剖面文件"，内核就合格了。

**这是可判定的验收信号**，不是主观感觉。

## 2. 三段式

### A 段：内核 + 一种图，打通全链路

选 **`c4-container@1`** 作为第一种图。理由：

| 判据 | 为什么是它 |
|------|-----------|
| 覆盖面 | 同时用到 person/container/datastore/queue/external、5 种关系、视图筛选、批注、约束 |
| 复杂度 | 比 context 高（有数据归属），比 component 低（无需 parent 层级） |
| 已有样本 | `examples/payments-arch.cvn.yaml` 与 `examples/covenant-self.cvn.yaml` 都基于它 |
| 布局 | 标准分层布局（ELK），能验证布局接口是否正确 |

A 段验收：`parse → validate(L0–L3) → layout → scene → SVG`，且 `examples/payments-arch.cvn.yaml` 能出图。

### B 段：自举第一轮（工具接管手写图）

把 `examples/covenant-self.cvn.yaml` 真正渲染出来——**用 Covenant 描述 Covenant**。

这一步一定会暴露问题。事实上**手写阶段已经暴露了 6 个**（见 `examples/README.md`），B 段要做的是让工具复现并处理它们。

> 关键认知：自举不是"等工具做完才开始"。我们**已经用"手写 `.cvn`"完成了半次自举**——它发现了 ELK 体积、审计事务、region 锚定三个硬伤。工具只是把这种检查自动化。

B 段验收：自举图能被校验、能渲染、批注能在图上显示；且新增的 3 个"表达不出来"的点被记录。

### C 段：缺口驱动扩展

循环：

```
画一张"这个剖面在 Covenant 里承担什么"的图
        │
        ├─ 画得出来 → 通过；该剖面毕业
        └─ 画不出来 → 诊断：
               ├─ 只是缺 kind/关系 → 加剖面数据（便宜）
               ├─ 缺通用能力（如有序消息、基数） → 改内核或加通用机制（贵，需评审）
               └─ 缺交互/呈现 → 归渲染层，不动语义
        ↓
      修复 → 复跑同一张图 → 直到画得出来
```

扩展顺序（也是 M2–M3 的顺序）：

| 序 | 剖面 | 会逼出什么新能力 |
|:--:|------|------------------|
| 1 | `dfd@1` | **记法变体**（demarco/gane-sarson）+ frame 信任边界 |
| 2 | `er@1` | **基数/角色**语义（关系的属性） |
| 3 | `flowchart@1` | 控制流分支与可达性规则 |
| 4 | `sequence@1` | **专用布局接口**（sequencer，非 ELK）——最容易暴露内核/渲染耦合问题 |
| 5 | `state@1` | 初始/终止态的基数规则 |
| 6 | `deployment@1` | **嵌套容器**（artifact 在 node 内） |
| 7 | `graph@1` | 大图 + 代码派生导入 |

> 先做 `dfd` 而不是 `er`：DFD 只加"记法变体"这一个新机制，是渐进的一步；ER 要动关系语义（基数），跨度更大。

## 3. 停止条件（何时冻结内核 v1）

三条同时满足：

1. **12 件套里每一件都能用对应剖面描述"它在 Covenant 中的角色"**，且无需手改渲染结果；
2. **连续 3 轮新增剖面，内核零改动**；
3. **自举图本身通过 L0–L6 全绿**（包括我们给它写的 fitness 规则）。

满足后内核冻结为 `kernel@1`，之后改动需 ADR + 迁移说明。

---

## 4. 防自嗨规则（重要）

自举最大的风险是变成"给自己画图"的无限循环：

| 规则 | 内容 |
|------|------|
| R1 每轮最多 3 个缺口 | 多了必然发散；超出记入 backlog 不处理 |
| R2 只修影响当期交付的 | "能画但画得不好看"推迟到 M2 之后 |
| R3 自举图不是产品 | 它是回归测试，不追求美观 |
| R4 每轮必须产出可执行结果 | 一个通过的校验、一张渲染出的图、一条关闭的批注——不接受"讨论了" |
| R5 时间盒 | 自举环节不超过当期工时的 20% |

---

## 5. 自举的双重用途

1. **格式回归测试**：Covenant 自己是最复杂的真实用例（多剖面、批注、约束、fitness）。
2. **缺口发现器**：比写测试更早发现"语义表达不出来"，因为测试只能验证你想到的，自举会暴露你没想到的。

---

## 6. 对 M1 计划的调整（垂直切片优先）

原 M1 是"4 个剖面 + 校验 L0–L3"（横向），**建议改为纵向切片**：

| 原计划 | 调整后 |
|--------|--------|
| M1：core + 4 剖面 + check | M1：core + **c4-container 一个剖面**，打通 `check → layout → SVG` |
| M2：layout + render | M2：**自包含 HTML（只读）+ 自举图渲染** |
| M3：editor + 批注 | M3：标注 + 导出补丁 + apply |

**理由**：你的核心体验是"打开 HTML 在图上标注"。越早看到真实产物，越早校准格式；否则可能把 4 个剖面都实现完，才发现视图/坐标模型不对。

**代价**：单剖面下 M1 显得"功能少"；但风险暴露得早。

**折中**：M1 内 c4-container 走全链路，`dfd`/`er` 只做 `check`（不渲染），这样横向也不算完全丢掉。
