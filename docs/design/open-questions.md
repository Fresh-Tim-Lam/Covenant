## 第一部分：已定决策（D1–D4）

### D1 技术栈 = TypeScript 全栈 ✅

- **内容**：`core`（文档模型/解析/序列化）、`profile`、`validate`、`layout`、`render`、`ai`、`cli`、`mcp`、`editor` 全部 TypeScript（strict）。
- **理由**：一份代码浏览器 + Node 通用；SVG/DOM 原生；AI 生成质量高；无需双语言工具链。
- **后果**：
  - 目录用 pnpm workspace monorepo（见 engine 文档 §5）。
  - 不需要 Rust/Python；性能问题以"视口裁剪 + 增量布局"解决。
  - **若后续要单二进制 CLI，再加编译层（bun build / node SEA），不改架构。**
- **不可逆性**：低（接口已按语言无关设计）。

### D2 交付形态 = 自包含本地 HTML + 可选本地服务 ✅

- **内容**：用户主路径是**双击一个生成好的 `.html`**（离线、单文件、无 CDN）在上面标注；开发态可用 `covenant serve` 获得直写与 AI 实时通道。
- **理由**：用户明确描述的交互样例就是"打开生成好的本地 HTML"。
- **后果**（详见 [interaction-and-ai-loop.md](interaction-and-ai-loop.md)）：
  - 渲染器必须能打包成**单文件浏览器 bundle**，且体积受控（目标 < 500 KB）。
  - 写回默认走 **C1 导出补丁**（因 `file://` 不能写盘）；`serve` 环境下升级为直写。
  - 字体、图标、主题全部内联或走系统字体栈。
  - **不做 Electron/Tauri 桌面壳作为首期形态**（HTML 已满足"本地打开"），需要时再包。
- **不可逆性**：中（若之后改桌面优先，打包思路要重做；但 Web 产物仍可复用）。

### D3 MVP 图集 = 12 件套 ✅

- **内容**：C4 三层（context/container/component）+ DFD + ER + 序列 + 状态 + 流程 + 部署 + 依赖图 + ADR（非图）+ 约束（非图）。
- **理由**：覆盖日常架构沟通 90%；其余 43 种通过"新增剖面"扩展，不进 MVP。
- **后果**：
  - 剖面按此顺序增量交付：C4 → DFD → ER → 流程 → 序列 → 状态 → 部署 → 依赖图。
  - 校验规则只对这 10 个剖面写内置规则；其他剖面走通用 L0–L3。
- **不可逆性**：低（只影响排期，不影响架构）。

### D4 本会话（M0）= 只出提案，不写代码 ✅

- **内容**：本阶段交付调研 + 格式 + 引擎 + 交互 + 示例；不生成 `src/`、不跑构建。
- **理由**：本会话 shell 不可用（pwsh 初始化失败，`exit 3221225794`），无法编译/测试；写未验证的代码风险高于收益。
- **后果**：M1 必须在**能运行 node/pnpm 的会话**中开始；`AGENT.md` 与 `docs/conventions/` 骨架也在 M1 一并生成。

## 第三部分：反方论证（保留，供未来复盘）

| 反对意见 | 回应 |
|----------|------|
| "Structurizr 已经能做架构即代码" | 只有 C4、DSL 自研、无自由画布、无元素级批注、无 AI 补丁协议。我们要的三点它都不做。 |
| "Excalidraw + Mermaid 插件就够了" | 画布无语义、Mermaid 有损且布局不可控；"能画"≠"能校验"。 |
| "LikeC4 已经很现代" | 最接近的对标；但缺批注与自由标注，且是 C4 专用而非通用内核。 |
| "YAML 做图格式太弱" | 语义层只需文本；复杂视觉放 `canvas` 层。diff 与手写体验优于 XML/JSON。 |
| "会不会没人用？" | 最大风险。缓解：先自举——用 Covenant 描述 Covenant 自己的架构。 |
| "为什么不直接在飞书画板上加语义？" | 格式封闭、不可编程、不可校验；且我们要的是"契约"不是"文档"。 |
