# 软件工程图示全景与"够不够用"判据

> **用途**：回答"DFD / ER / 流程图 是不是全部图种类、我漏了什么、怎样才算没有歧义"，并给出 Covenant 的剖面规划。
> **目标读者**：项目负责人（确认范围）、AI Agent（实现剖面时的词表来源）。
> **状态**：提案 v0，核验于 2026-11-03。
> **关联文档**：[landscape-2026-11.md](../research/landscape-2026-11.md)（对标）；[format-spec-v0.md](format-spec-v0.md)（剖面如何落地为格式）。

---

## 1. 直接回答

**没有"软件工程图的完整清单"，也不可能穷举。** 原因不是业界偷懒，而是"图"本质上是**模型的视图（view）**，不是**类型（type）**——ISO/IEC/IEEE 42010 把这件事说得很清楚：架构描述由**视点（viewpoint）**约束**视图（view）**，模型可以投影出无限多视图。

但**可以穷举"维度"**。你列的 DFD / ER / 流程图 只覆盖了 3 个维度中的 2 个，**漏掉了最关键的"结构/部署/约束/风险"**。下面第 2 节是全景，第 5 节是判据。

## 3. 为什么"穷举图类型"是错的

1. **标准分属不同体系且互相重叠**：UML 状态机 / Harel statecharts / BPMN 子流程 都在描述状态；DFD 有 Yourdon-DeMarco 与 Gane-Sarson 两套不兼容符号。强行合并 = 制造歧义。
2. **标准在持续演进**：SysML v2 重构了类型体系与文本记法；UML 仍在修订；42010 已换版。任何"清单"两年后即过时。
3. **领域图不在标准里但真实存在**：威胁模型、数据谱系、特征模型、能力地图、团队拓扑，没有一个是 UML 图。
4. **图是视图不是类型**：同一模型可以有无数投影（C4 的 4 层是同一模型 4 个缩放；同一组件图可出"正常流"和"故障流"两张）。**种类天然开放。**

**结论**：与其维护一张永远不全的清单，不如维护**一个能描述任意图的元模型**。这就是 Tier-0 内核 + Tier-1 剖面的由来。

## 4. 歧义的真正来源与解法（这才是"无歧义"的工程答案）

| 歧义来源 | 典型症状 | Covenant 的解法 |
|----------|----------|-----------------|
| S1 记法混用 | DFD 里画了 UML 箭头；Chen 和 crow's foot 混着画 | **剖面锁定记法**：`profile: dfd` + `notation: demarco`，非法符号直接报错 |
| S2 语义缺失 | 看不出箭头是数据流、控制流还是依赖 | **关系类型来自剖面的关系矩阵**，不是自由字符串 |
| S3 跨图不一致 | 上下文图有"支付服务"，容器图里没有 | **单一事实源**：元素只在 `elements:` 定义一次，视图引用；跨文档用 `imports:` |
| S4 图文漂移 | 文档说 A，图说 B，代码是 C | **图 ↔ 文档 ↔ 代码三方锚点**（`links:`）+ 一致性校验（fitness） |
| S5 团队默会知识 | "这个框你懂的" | **`summary` / `constraints` 强制必填**，AI 与新人靠它理解 |
| S6 AI 自由发挥 | AI 改图后结构悄悄变了 | **AI 只能提交语义补丁 + 校验 + 语义 diff + 人工批准** |

> 一句话：**消歧义靠"语义可判定"，不靠"图类型够多"。** 一张语义明确的活动图，胜过五张语义含糊的图。

**12 件套**（10 张图 + 2 个非图一等对象），覆盖日常架构沟通的 90%：

| 序 | 对象 | 剖面 | 为什么必须有 |

| 3 | 组件视图 | `c4-component` | 模块边界与内部依赖 |
| 4 | 数据流图 + 信任边界 | `dfd` | 数据从哪到哪、哪里不可信 |
| 5 | ER / 数据模型 | `er` | 数据契约 |
| 6 | 序列图 | `sequence` | 时序与调用契约 |
| 7 | 状态机 | `state` | 状态与非法迁移 |
| 8 | 流程图 | `flowchart` | 业务/处理决策 |
| 9 | 部署图 | `deployment` | 环境与节点约束 |

## 6. "图够不够用"的判据（替代清单）

不要问"我还缺哪种图"，而要问**这 6 个问题有没有明确答案**：

1. **边界**：系统是什么、不是什么、外部有谁？ → C4-C1 / DFD 外部实体
2. **组成**：内部由什么构成、谁依赖谁？ → C4-C2/C3 / 依赖图
3. **数据**：数据存成什么样、怎么流动、谁改它？ → ER / DFD / 谱系
4. **时序**：一次关键操作用什么顺序发生？ → 序列图
5. **状态**：有哪些状态、哪些迁移非法？ → 状态机
6. **运行与风险**：部署在哪、哪里会坏、信任边界在哪？ → 部署图 / 威胁模型

**六问皆有答 = 图够用；六问有空白 = 补那一格，不必补种类。**
这套判据本身就是给 AI 的提示词模板（见 `format-spec-v0.md` §7 的 AI 投影约定）。

## 7. 剖面与视图的正交关系

一个剖面 ≠ 一张图。正确的关系是：

```
剖面(profile)  定义：允许哪些元素类型 / 关系矩阵 / 必填属性 / 校验规则 / 布局默认值
视图(view)     选择：用哪些元素、什么布局、什么标注、什么过滤器
文档(document) 实例：一个 .cvn 文件 = 1 个剖面 + N 个视图 + 共享元素定义
```

例：`c4-container` 剖面下可以有 3 个视图——「正常请求流」「故障降级流」「数据分类视图」，**共享同一份 `elements:`**，只有筛选与标注不同。这就是"不会出现跨图不一致"的结构性保证。
