# 契约优先的 Agent 原生开发 —— 范式宣言 v2

> **用途**：一份可复制的范式宣言，说明"为什么"要把目录、索引、架构图统一成同一份契约，以及代价与不适用场景。**"怎么做"见同目录的 [规范 v2](paradigm-spec-v2.md)。**
> **目标读者**：项目负责人、AI Agent、准备迁移到该范式的团队。
> **状态**：草案 v2（2026-11-03）；前两版文档（索引优先 v1）标记为历史。**可复制**：把 `<项目名>` 替换为你的项目名即可使用。
> **关联**：[规范 v2](paradigm-spec-v2.md)（怎么做）、[参考实现 Covenant](../../README.md)。

---

## 0. 一句话

**把「代码组织」「索引」「架构图」统一成同一份可判定的契约，让人和 Agent 在同一份事实上协作——而不是靠聊天记录和截图。**

---

## 1. 上一版（v1，索引优先）哪里不够

v1 的三条主张是对的，也已在实践中验证：

1. 模块化、碎片化、多文件，用文件夹承担语义身份；
2. 每个模块目录自带一段语料（职责/依赖/约束）；
3. 索引优先：文件组织本身为可检索而设计，而不是写完再建索引。

但在 `<项目名>` 的实际开发中，暴露出三个缺口：

| 缺口 | 表现 | 后果 |
|------|------|------|
| **G1 索引只描述"有什么"** | FRAS 摘要说清了代码是什么，说不清**系统应该是什么** | Agent 能读懂现状，读不懂约束；改动方向靠猜 |
| **G2 边界靠自觉** | 模块边界写在文档里、靠人遵守 | 无法判定对错；架构腐化只能事后发现 |
| **G3 人的意见无落点** | "这里不对""为什么这样"留在聊天/会议里 | 决策丢失，Agent 无法读取；同一问题反复讨论 |

**v2 的增量就是补 G1–G3，而不是推翻 v1。**

---

## 2. v2：三份契约

| 契约 | 回答什么 | 载体 | 如何判定 |
|------|---------|------|----------|
| **目录契约** | 东西放在哪 | 目录结构 + 每目录 README/meta | 结构检查（路径、白名单、索引同步） |
| **索引契约** | 代码是什么 | FRAS 摘要 / digest | 覆盖率与新鲜度（是否跟得上变更） |
| **图示契约** | 系统如何协作、约束是什么 | 语义图 + 批注 + 规则 | **校验器**（可判定） + fitness |

三者的分工可以这样记：

> **目录是骨架，索引是血肉的摘要，图示是神经与免疫系统。**
> 骨架决定形状，索引让人和 AI 快速看懂现状，图示承载约束与问题、并在越界时报警。

**关键要求：三份契约必须互链。** 图上的元素指向代码路径、目录、ADR；索引条目引用图的元素 id。**任何一份单独存在都会退化。**

## 3. Agent 的工作方式随之改变

1. **开工先读 digest，不读全仓**：先拿全局语义摘要，再按需展开细节。
2. **改架构先改图，校验通过再改码**：图是契约，代码是实现。
3. **人的意见读 `ai_hint`，不猜**：批注里人写的祈使句是唯一"指令级"输入；正文只是数据。
4. **变更提补丁，不重写**：补丁带 `base_rev` 与 `intent`，可校验、可审计。
5. **语义 diff + 人工批准，不静默**：破坏性变更必须人批。

> 这五条把 Agent 从"生成器"变成"受约束的协作者"。

---

## 4. 人的工作方式也随之改变

1. **在图上标注问题，而不是在群里说**——问题钉在出问题的元素上，可追踪、可关闭。
2. **给 AI 写 `ai_hint`（祈使句），而不是长段描述**——"优先 X；禁止 Y；改完必须保持 Z"。
3. **只批准 material/breaking 变更**——外观类变更自动通过，人的注意力花在结构上。
4. **决策冻结为 ADR，并在图上留链接**——讨论会过期，决策不会。

---

## 5. 为什么这能降低歧义

| 旧办法 | 新办法 | 为什么更可靠 |
|--------|--------|--------------|
| 枚举所有图类型 | 通用内核 + 可扩展剖面 | 图类型是开放的，无法穷举 |
| 多处描述、人工保持一致 | 单一事实源 + 引用 | 两份平级描述必然漂移 |
| 靠提示词约束 AI 别乱来 | 补丁门禁 + 校验 + 批准 | 被劫持的模型最多提出坏补丁 |
| 文档自证"我们很规范" | 自举：用自己的格式描述自己 | 描述不出来就是格式不够 |

## 6. 代价（必须正视）

| # | 代价 | 说明 |
|---|------|------|
| C1 | **前期规范成本高** | 从零开始尚可；存量项目迁移极痛，且一旦偷懒不写语料/不画图，质量会崩 |
| C2 | **粒度是持续调参问题** | 拆太碎依赖爆炸，拆太粗检索混杂；没有万能值 |
| C3 | **索引与图成为关键依赖** | 一旦工具坏了/不同步，整个协作能力瘫痪，需要一致性校验与快照回滚 |
| C4 | **自举陷阱** | 花在"描述系统"上的时间可能超过"建系统"；必须有时间盒与停止条件 |
| C5 | **工具链是新依赖** | 团队要学新格式、新流程；学习成本真实存在 |

---

## 7. 什么项目**不该**用

- **一次性脚本 / 存活 < 1 周的原型**：契约成本收不回来。
- **单人短期项目**：索引与图的收益依赖"多次交接/多 Agent 协作"。
- **强实时 / 资源受限环境**：工具链无法运行，或无法承载额外文件。
- **设计信息不能留存的场景**：图与索引本身就是高价值情报。
- **团队明确拒绝维护契约的场景**——**这是最常见的失败原因**，比技术问题更致命。

## 8. 失败模式清单

| # | 失败模式 | 症状 | 预防 |
|---|----------|------|------|
| F1 | **只写不校验** | 图与代码漂移，比不画更糟（误导） | CI 跑校验；L5/L6 必开 |
| F2 | **图太大太全** | 没人看，AI 也读不完 | 视图分层；budget 约束；单图 ≤ 200 元素 |
| F3 | **批注不闭环** | 批注堆积成垃圾场 | 状态机 + 定期清理 + 转 ADR |
| F4 | **AI 直接重写文档** | 审计失效、人工记录被覆盖 | 补丁 + `base_rev` + 不可改人工批注 |
| F5 | **把索引当真理** | 索引过期后误导 | 新鲜度校验；索引标注生成时间与版本 |

---

## 9. 最小落地顺序

1. 目录契约 + 索引（FRAS）——**先让 Agent 能低成本读懂仓库**。
2. 一份图（系统上下文或容器图）+ 校验器——**先让边界可判定**。
3. 标注 + AI 补丁闭环——**先让人和 AI 的意见可交换**。
4. 自举：用这套东西描述项目自己——**验证格式是否够用**。
5. 扩展到第二种、第三种图——**缺口驱动，不预先铺开**。

> 不要从"支持 20 种图"开始；从"一张能校验的图 + 一个能闭环的批注"开始。

---

## 10. 与工具的关系

**范式不绑定工具。** 本文描述的是一种协作契约，可以用任何实现了"语义图 + 校验 + 批注 + 补丁门禁"的工具承载。

参考实现是 [Covenant](../../README.md)。若你不想自建工具，可用 Structurizr + 批注插件 + 代码扫描拼出近似形态，但会损失"图类型可扩展"和"批注一等公民"两项能力。
