# 契约优先的 Agent 原生开发 —— 规范 v2（可校验）

> **用途**：把 [范式宣言 v2](paradigm-declaration-v2.md) 的"为什么"落成"怎么做"——目录、索引、图示三份契约的可执行细则、模板与自检清单。目标：**新项目 1 天内搭完骨架，并由 CI 持续校验**。
> **目标读者**：项目负责人、AI Agent、迁移团队。
> **状态**：草案 v2（2026-11-03）。**可复制**：把 `<项目名>` 替换为你的项目名。
> **关联**：[宣言 v2](paradigm-declaration-v2.md)；参考实现 [Covenant](../../README.md)。

---

## 0. 名词

| 名词 | 定义 |
|------|------|
| **三契约** | 目录契约（放哪）、索引契约（是什么）、图示契约（怎么协作/约束） |
| **模块** | 一个目录 = 一个语义单元，有唯一职责与明确边界 |
| **契约条目** | 索引里的一条 FRAS 记录，或图里的一个元素/关系 |
| **补丁** | 对契约的结构化变更（不是自由文本编辑） |
| **判定方式** | 该规则由谁检查：`CI`（自动）/ `Review`（人工）/ `Self`（自查） |

> **一条铁规**：凡是**无法判定**的规则，不写进本规范（可以留在宣言里当理念）。规范里只有能被检查的句子。

## 1. 适用范围与前提

### 1.1 应当使用

- 项目寿命 **> 1 个月**；
- 协作者 **≥ 2**（人类与 Agent 混算），或需要跨会话交接；
- 能够运行 **CLI 与 CI**（本地或流水线）。

### 1.2 不应使用（判据，不是情绪）

| 情形 | 判据 |
|------|------|
| 一次性脚本/原型 | 预期代码量 < 2k 行 且 寿命 < 2 周 |
| 无法运行工具链 | 受限环境、无 CI、无本地执行权限 |
| 设计信息不可留存 | 合规要求禁止把架构落盘 |
| 团队拒绝维护契约 | 无人愿意承担"契约维护者"角色——**这是最常见的失败原因** |

### 1.3 前提

1. Git（或其他版本控制）；
2. 一个能执行三件事的 CLI：**校验、生成摘要、应用补丁**；
3. 全仓库 UTF-8；
4. 默认不联网（见宣言 §10）。

## 2. 目录契约

### 2.1 一级目录（唯一落位）

| 目录 | 职责 | 允许临时文件 |
|------|------|:---:|
| `src/` | 正式源码 | ❌ |
| `tests/` | 正式测试 | ❌ |
| `docs/` | 文档中心（规范/设计/参考/指南） | 仅 `docs/tmp/` |
| `scripts/` | **可复用**开发工具 | ❌ |
| `resources/` | 随应用分发的静态资源 | ❌ |
| `config/` | 本机配置样例（真实配置 gitignore） | ❌ |
| `artifacts/` | **全仓唯一临时区**（gitignore） | ✅ 仅此 |
| `logs/` | 调试日志（gitignore） | ✅ |
| `arch/` | **图示契约**（`.cvn` 项目目录） | ❌ |
| `packaging/` | 打包发布（可选） | ❌ |

### 2.2 根目录白名单

`README*`、`AGENT.md`、`LICENSE`、包清单/构建入口、`.gitignore`、`.gitattributes`、CI 配置、`THIRD_PARTY_NOTICES.md`。**其他一律归位。**

### 2.3 临时文件铁律

一次性脚本、截图、诊断 JSON、实验代码 → `artifacts/`（已 gitignore + 根级兜底模式）。
**禁止出现在**：仓库根、`src/`、`scripts/`、`docs/` 正文、`arch/`。

### 2.4 模块语料（每个业务模块目录必须）

```markdown
# <模块名>

> **职责**：<一句话，独立可读，禁止"详见 xxx">
> **边界**：<不做什么 / 不属于本模块的东西>
> **依赖**：<允许依赖谁；禁止依赖谁>
```

可选 `meta.yaml`：

```yaml
module: payments
owner: human:lily
entrypoints: [pay/application/*]
side_effects: [writes ledger db, calls psp]
invariants: ["所有写接口幂等", "禁止两阶段提交"]
```

### 2.5 判定

| 编号 | 规则 | 判定 |
|:---:|------|:---:|
| D1 | 每个一级目录有 `README.md`，首行即职责 | CI |
| D2 | 根目录无越权文件（白名单外） | CI |
| D3 | `artifacts/` 与 `logs/` 已 gitignore | CI |
| D4 | 每个 `src/` 下的业务模块目录有 README 且含职责/边界/依赖 | CI |
| D5 | 无 `tmp_`/`debug_`/`repro_` 前缀的正式文件混入 `src/` | CI |
| D6 | 目录增删后父目录索引已同步 | Review |

## 3. 索引契约

### 3.1 FRAS 条目（每个源文件或模块一条）

```yaml
file: pay/application/PaymentService.kt
f: 支付授权/捕获/退款编排入口          # File 职责，≤ 60 字
r: [pay/domain/Order.kt, pay/port/PspClient.kt]   # 必读依赖
a: [pay/api/CheckoutController.kt]     # 上层调用者
s: ["写接口必须幂等", "禁止两阶段提交"]  # 代码推不出的隐性约束
```

### 3.2 更新规则

| 触发 | 动作 | 判定 |
|------|------|:---:|
| 代码变更（git diff） | 增量更新受影响条目的 F/R/A/S | CI |
| 新增文件 | 必须有对应条目 | CI |
| 删除文件 | 条目标记 `orphan` 并移除 | CI |
| 目录移动 | 条目路径同步 + 交叉引用修正 | Review |

### 3.3 新鲜度

条目记录 `source_sha256` 与生成时间。**源码 hash 变化但条目未变 → stale**，CI 失败。

### 3.4 读写隔离

- 索引写入者：专用 Indexer（人或 Agent，独占）。
- 其他协作者：**只读**。改动代码后触发重新生成，不手改索引。

### 3.5 判定

| 编号 | 规则 | 判定 |
|:---:|------|:---:|
| I1 | `src/` 下每个文件有 FRAS 条目 | CI |
| I2 | 无 stale / orphan 条目 | CI |
| I3 | 条目 `f` 非空且独立可读（禁止"详见"） | CI（正则）+ Review |
| I4 | 索引文件被其他角色手改 → 报错 | Review |

## 4. 图示契约（v2 的核心增量）

### 4.1 最小图集

**先 1 张**：系统上下文 **或** 容器视图（二选一）。
扩展条件：当"AI/新人理解某模块需要额外 30 分钟以上"时，再加对应图；**不预铺**。

| 图 | 何时加 |
|----|--------|
| 系统上下文 | 项目启动即有外部依赖 |
| 容器/服务视图 | 有 ≥2 个部署单元 |
| 数据模型 / 数据流 | 有持久化且多人改 |
| 时序图 | 存在跨服务异步/重试/幂等设计 |
| 部署图 | 有环境差异 |

### 4.2 必填字段（元素/关系）

| 对象 | 必填 |
|------|------|
| 元素 | `id`、`kind`（来自记法词表）、`name`、`summary`（一句话职责） |
| 关系 | `id`、`kind`、`from`、`to`、`summary`（这条连接做什么） |
| 文档 | `purpose`（回答什么问题）、`non_goals`（不表达什么） |
| 批注 | `type`、`severity`、`title`、`status`、`author`、`target` |

> `non_goals` 与 `summary` 同样是给 AI 的降歧义字段，不可省。

### 4.3 校验分级

| 级 | 检查 | 必须通过 |
|:--:|------|:---:|
| L0 | 语法（禁锚点/别名/重复键） | ✅ |
| L1 | 结构 schema（字段/类型/未知字段） | ✅ |
| L2 | 完整性（ID 唯一、引用不悬空、父子无环） | ✅ |
| L3 | 记法（kind 在词表、关系符合矩阵、必填属性） | ✅ |
| L4 | 跨文档（引用可解析、无重复定义） | ✅ |
| L5 | 代码锚点（`links.kind=code` 可解析） | 推荐 |
| L6 | 架构规则（分层、禁止依赖、无环） | 推荐 |

### 4.4 Finding 必须可执行

```yaml
code: rule/relation-matrix
level: L3
severity: error
element_id: r.pay-ledger
message: "writes 的目标必须是 datastore 或 queue，当前是 container"
fix_hint: "把 e.outbox-relay 的 kind 改为 worker，或改为对 e.outbox 的 writes"
auto_fixable: false
```

**禁止空话**：不得出现"请检查配置""建议优化"这类无法执行的 `fix_hint`。

### 4.5 批注与 `ai_hint` 写法

批注是人的意见的**结构化落点**，`ai_hint` 是唯一被 AI 当作指令消费的字段。

| 规则 | 内容 |
|------|------|
| H1 | `ai_hint` 必须是**祈使句**：以动词开头，或"优先/禁止/必须 + 动词"开头；不写陈述句 |
| H2 | 只写"做什么/不做什么/必须保持什么"，不写背景（背景放 `body`） |
| H3 | 规范建议 ≤ 200 字（工具硬上限 2048 字符）；超了说明约束过多，应拆批注 |
| H4 | 禁止模糊词：尽量、考虑、适当、优化一下 |
| H5 | 若涉及不可逆操作，必须写明"需人工批准" |
| H6 | AI 只能追加 `thread`，不得改人工批注的 `status`/`body` |

反例 / 正例：

```yaml
# ❌ 反例
ai_hint: 这里性能不太好，看看能不能优化一下。

# ✅ 正例
ai_hint: 把 r.pay-ledger 改为异步 outbox；禁止引入两阶段提交；改完保持写接口幂等。
```

### 4.6 图与代码互链

至少一条链：图元素 → 代码路径（`links.kind=code`）或 → ADR。
**图不指向任何代码/决策的元素**，视为装饰，CI 给 warning。

### 4.7 判定

| 编号 | 规则 | 判定 |
|:---:|------|:---:|
| G1 | L0–L4 全绿 | CI |
| G2 | 每个元素有 `summary`；每份文档有 `purpose`/`non_goals` | CI |
| G3 | 每条关系符合记法矩阵 | CI |
| G4 | `ai_hint` 通过句式检查（祈使句、长度、无模糊词） | CI（规则库） |
| G5 | 每条 `fix_hint` 含具体 id 或具体字段路径 | CI（正则） |
| G6 | 人工批注未被 AI 修改 | CI |
| G7 | 每个元素至少一条 code/ADR 链接 | CI（warning） |
| G8 | 图规模 ≤ 200 元素/视图（超了拆图） | CI |

## 5. 补丁与批准流程

### 5.1 补丁结构

```yaml
change:
  doc: arch/containers
  base_rev: 4              # 必填，乐观锁
  intent: <一句话说明为什么改>
  related_annotations: [a.xxx]
  ops: [...]               # RFC 6902 JSON Patch
```

### 5.2 语义 diff 三类

| 类 | 例子 | 处理 |
|----|------|------|
| `cosmetic` | 移动、换色、改主题 | 自动通过 |
| `material` | 增删关系、改属性、加元素 | 人确认（可配置超时） |
| `breaking` | 删除仍被引用的元素、改关系主语义 | **强制人工批准** |

### 5.3 批准矩阵

| 变更 | 谁批 |
|------|------|
| cosmetic | 无需 |
| material（非 core 模块） | 模块 owner |
| material（core/公共契约） | 契约维护者 |
| breaking | 契约维护者 + 相关 owner |

### 5.4 审计

每次写入记录：`at / actor / action / doc / base_rev / new_rev / intent / ops_sha256 / findings / diff_class / approved_by`。
**先写 intent，再落盘，再写 commit**（write-ahead，崩溃可回放）。

### 5.5 判定

| 编号 | 规则 | 判定 |
|:---:|------|:---:|
| P1 | 补丁缺 `base_rev` 或 `intent` → 拒绝 | CI |
| P2 | `breaking` 无 `approved_by` → 拒绝 | CI |
| P3 | 补丁改人工批注/owners → 拒绝 | CI |
| P4 | 审计缺字段 → 拒绝 | CI |

## 6. 最小角色（不做组织设计）

| 角色 | 负责 | 可由同一人或 Agent 兼任 |
|------|------|:---:|
| 契约维护者 | 目录/索引/图示三份契约的最终裁决 | ✅ |
| 模块实现者 | 自己模块内的代码 + 语料 + 图元素 | ✅ |
| 守卫 | 跑校验、盯漂移、拒绝违规补丁 | ✅ |

> 规范只约束"谁对哪份契约负责"，**不规定团队编制**。人数少时一人全兼也可以。

## 7. 新项目 0→1（半日到 1 天）

| 步 | 动作 | 产出 | 预计 |
|:--:|------|------|------|
| 0 | 确认 §1.1 三条前提 | 一页事实清单 | 5 min |
| 1 | 建目录骨架 + 每目录 README | 目录树 | 30 min |
| 2 | `AGENT.md`（八节：Role/TechStack/Commands/Architecture/Conventions/Boundaries/Pitfalls/References） | 接入指南 | 40 min |
| 3 | 根级配置：`.gitignore`（含 artifacts/logs + 兜底模式）、包清单、LICENSE | 可构建仓库 | 20 min |
| 4 | 索引：跑一次全量生成 FRAS | 索引基线 | 30 min |
| 5 | 图示：写 1 张上下文/容器图，L0–L4 通过 | 第一份契约 | 40 min |
| 6 | 接入 CI：校验 + 索引新鲜度 + 目录检查 | 门禁 | 40 min |
| 7 | 自检清单（§9）全过 + 提交 | 可协作仓库 | 15 min |

**验收**：另一个 Agent 只读 `AGENT.md` + 索引 + 第一张图，就能说出"系统边界、主要容器、三个硬约束"，**不需要读源码**。

## 8. 度量（每迭代看一次）

| 指标 | 目标 | 采集 |
|------|------|------|
| 检索 token 开销 | 比"全仓盲扫"降 ≥ 60% | 索引命中率 × 平均上下文长度 |
| 校验通过率 | L0–L4 ≥ 95% | CI 报告 |
| 批注闭环率 | 30 天内 resolved ≥ 70% | 批注状态统计 |
| 图码漂移数 | 每迭代 ≤ 2 | L5/L6 失败数 |
| 自举通过率 | 项目能用自己的图描述自己 | 人工季度评审 |
| 补丁拒绝率 | 5%–20%（太低=没门禁，太高=规则过严） | 审计日志 |

## 9. 自检清单（Definition of Done）

**仓库级**
- [ ] 每个一级目录有 README 且首行即职责
- [ ] 根目录无越权文件；`artifacts/`、`logs/` 已忽略
- [ ] `AGENT.md` 八节齐全，Boundaries 分 Always / Ask First / Never
- [ ] 索引：无 stale/orphan，每个源文件有条目
- [ ] 图示：至少 1 张，L0–L4 全绿
- [ ] 每条 `ai_hint` 通过句式检查
- [ ] 审计字段齐全，write-ahead 生效
- [ ] CI 跑通四个门禁：目录 / 索引 / 图 / 补丁

**变更级（每次提交）**
- [ ] 改了代码 → 索引已更新
- [ ] 改了结构 → 图已更新且校验通过
- [ ] 有架构决策 → 写了 ADR 并在图上链接
- [ ] 有 `breaking` 变更 → 有批准记录

## 10. 存量项目迁移（三阶段）

| 阶段 | 做什么 | 风险控制 |
|:----:|--------|----------|
| 1 | 只上**索引**：先让 Agent 能低成本读懂仓库 | 不改代码结构；索引可随时删除重建 |
| 2 | 加**一张图**（选最痛的那块），只画现状不画理想态 | 图与代码不一致时**以代码为准**，先记录差异不改码 |
| 3 | 接**批注闭环**：把已知问题钉到图上 | 先只读模式，稳定后再开补丁通道 |

**禁止**：一次性重构目录 + 补索引 + 画全部图。存量项目这样干必然烂尾。

## 11. 规范自身的可执行性

1. **本规范必须能在 1 天内落地**（§7 时间盒）。超过 = 规范太重，裁剪。
2. **每条规则必须有判定方式**（CI / Review / Self）。没有判定方式的句子应删除。
3. **规范变更走 ADR**，并同步更新本文件的版本号与变更记录。
4. 本规范**不绑定工具**；工具只需满足 §1.3 的三个能力 + 图示的四项能力（解析/校验/批注/补丁）。
