# 文件粒度与文件夹语义（L12）

> **一句话**：**文件夹承载高一级语义，文件只承载一个可命名的职责。**
> 目标不是"代码好看"，而是**让任何引用都不需要在文件内定位行列号**。

## 1. 为什么这条规则重要

旧做法的问题（本仓已实测）：

- `packages/render/src/html.ts` 2100+ 行，改动必须靠"第 1800 行附近"这类描述沟通；
  用脚本批量替换连续 3 次破坏模板字符串，48/52 个 DOM 测试全挂（见 AGENTS.md E2）。
- 大文件让**并行派发不可能**：两个 Agent 改同一文件必然冲突。
- 大文件让 **FRAS 索引失真**：一个 `f:` 描述无法覆盖 2000 行的多个职责，
  索引退化，Agent 只能整文件重读 → 烧上下文。

## 2. 规则（机器检查：`pnpm granularity`）

| 项 | 规则 |
|---|---|
| 新源码文件 | ≤ **300** 行 |
| 新测试文件 | ≤ **400** 行 |
| 存量文件 | **冻结**在当前行数，**只许减、不许增**（棘轮） |
| 子文件夹 | 必须有 `README.md`，说明该文件夹的语义契约（F/R/A/S） |

- **分工**：文件夹 = 语义单元（可被索引、可被单独派发）；文件 = 单元内的一个职责。
- **派发单位**：派任务时按**文件夹**派，不按"文件第 N 行到第 M 行"派。
- **引用写法**：`packages/render/src/viewer/annotation.ts`，**不写** `html.ts:1800-1850`。

## 3. 棘轮机制（为什么不是一刀切 300）

当前已有 14 个文件超标（最大 2114 行）。若一刀切 300，检查会**永久红**——红久了就没人看，
这是"绿灯疲劳"，不是治理（AGENTS.md L6）。

所以采用**棘轮**：

```
team/file-granularity.json
  max_new_file_lines: 300
  max_new_test_lines: 400
  grandfathered: { "packages/render/src/html.ts": 2114, ... }
```

- 存量文件的**当前行数被记为上限**：再涨就 FAIL，拆小了要同步下调基线。
- 新文件没有豁免，直接受 300/400 限制。

**唯一合法方向是下降。** 下降后跑 `pnpm granularity --init` 重建基线（并在提交里说明拆了哪个文件）。

## 4. 拆分动作（唯一允许的做法）

1. **一次只拆一个文件**，按**职责**拆，不按行数均分。
2. 新建文件夹 → 先写该文件夹的 `README.md`（语义契约）。
3. 拆一个文件 → 立刻跑一次对应测试（`packages/render` 改动必须跑 `html.dom.test.ts`）。
4. 全部绿后再 `--init` 更新基线，**不要**中途改基线掩盖增长。
5. ❌ 禁止用脚本批量改 `html.ts` 这类模板字符串大文件（AGENTS.md E2）。

## 5. 与派发契约的关系

- 写域（AGENTS.md §5）按 `packages/*` 划分；**文件夹是包内的二级派发单位**。
- L1 要求 spawn 前声明 `write_scopes`；拆分后 `write_scopes` 应精确到文件夹，而非整个包。
- 一个文件夹同一时刻只允许一个 Agent 写（写域建议锁 + L1 排队）。

## 6. 检查命令

```bash
pnpm granularity          # 人类可读，含"下降方向 Top5"
pnpm granularity --json   # 机器可读
node scripts/check-file-granularity.mjs --init   # 人工确认后重建基线
```

已接入 `pnpm verify`，因此**任何增长都会在 CI 上暴露**。
