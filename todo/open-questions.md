## Q1 ⭐ 编辑边界：用户"自己编辑"能编辑什么？

- **问题**：R-001 只说"架构图还得能够用户自己编辑"，未说明编辑对象。

  - **B（中）**：A + **增删元素/关系**、改关系方向；每次改动仍生成补丁并过校验。

  - **D（旧现状）**：只编辑批注（HTML 已支持）。

- **未回答前的默认假设**：**A**（风险最低、可逆、仍走补丁门禁）。**这只是 todo-scribe 的建议，未获用户确认前不得当作已同意。**

## Q2 ⭐ 前端编辑态通道：还要不要 `serve --edit` 即时预览？

- **问题**：**现状已定**——HTML 编辑态**导出 `edits.json` → 本地 `covenant edit` 应用**（D-012，已实测，不开端口）。问题因此收窄为：**是否还需要 `serve --edit` 做"改完即时预览"**？
- **为什么要问**：加 `serve --edit` 意味着新增本地写接口、用户需起端口（与 R-003 字面冲突），并需复核 Q9 / D-005。
- **可选方案**：
  - **A（现状，已实现）**：导出 `edits.json` → 人工跑 `covenant edit --diff` 预览、`--accept` 写回。不开端口、可离线，代价是"多一步人工"。
  - **B（可选增强）**：新增 `covenant serve --edit`，起**短时本地服务**，页面 POST `edits.json`，服务端跑 `covenant edit` —— 即时预览；需用户明确接受"编辑时才起服务"，并复核 D-005。
  - **C**：File System Access API 直接写目录 —— 已被项目决策 Q9 否决（仅 Chromium 支持、绕过校验）；如要启用需用户明确推翻 Q9。
  - **D**：不做前端编辑（退回只读 + 批注），编辑交给 CLI/Agent。
- **未回答前的默认假设**：**A 保持现状**（已实现、满足"不开端口"）；B 仅在用户明确要"即时预览"时做。
- **拍板（用户，2026-11-03，R-005 原话（二））**：选 **B（短时本地编辑服务）**；两条交付要求：①一键启动脚本 → `pnpm edit:serve`（`serve dist --edit --open`）；②"别的 Agent 团队把控的项目"的系统化部署指引 → `docs/guides/agent-team-edit-deployment.md`。**A 保留为无服务兜底；C 后续再加**（T13）。→ 决策 **D-021**（ADR-0004，accepted）。
